# Enterprise marketing claim audit

Reviewed 10 November 2026 against the local working tree. This is a static code audit, not a live merchant/production test. Application source was not changed. Paths below are relative to `/Users/xhurianshaba/Developer/zennit/ecentic/`; line numbers identify the inspected implementation. Supplied pilot/research facts are user evidence, not code-derived measurements.

## Source audit findings applied to the rebuild

1. **A listing Apply does not publish all three fields.** `approveProductListing` generates and publishes the title and HTML description. Structured data has a separate publish action. Do not describe one Apply as publishing title, description, and schema together.
2. **The rewrite does not consume competitor gaps.** `generateImprovedListing` receives the existing title, description, and win rate only. It does not receive a winning competitor or the simulation reasoning. Say that simulations identify opportunities and the rewrite reorganizes existing product facts, not that it fills the exact fields a winning competitor had.
3. **Merchant Center push is separate.** `pushOverrides` reads published listing records, but it is invoked from Google Shopping/settings controls. Listing Apply does not call it; the Google cron verifies/reconciles existing overrides, rather than pushing new ones. Use “Send your published fixes to Merchant Center” rather than “the same click publishes to your store and Google feed.”
4. **Agent controls are configurable.** An empty allow-list permits all platforms. Signatures are verified when supplied and mandatory only when the merchant enables `requireSignatures`. Say “configurable allow-lists, signature verification and rate limits,” not that every request is signed/every agent allow-listed by default.
5. **Developer interfaces do not export the dashboard's results.** REST discovery, MCP and CLI exist, but the seven MCP tools cover plans, keys, billing checkout, connection, and onboarding. No live traffic/results export tool or versioned REST endpoint was found. Remove “every result from your systems” and “pull tracking data through REST/MCP/CLI.”
6. **Scheduled rescans are disabled.** The implementation exists but the entry point explicitly returns `{disabled: true}` and the daily schedule is absent. Manual scans and the pending-scan worker are active implementations.
7. **Legacy profile generation remains invalid for modern UCP.** The AI output schema is `@type: Merchant` plus descriptive merchant fields, not a modern `ucp` discovery envelope. Do not advertise Dominate “UCP generation.” The separate hosted WooCommerce discovery implementation is real.
8. **PAYG attribution is store-wide fallback, not shopper linkage.** It uses an explicit cart tag if supplied, otherwise the latest referral anywhere on the store within the configured window (default 7 days). The checked `tracker.js` does not itself write the cart tag. Avoid claims of proven incremental sales or shopper-level attribution.
9. **Feed support is bounded.** XML RSS/feed entries and JSON arrays/`products`/`items` are accepted and mapped to a small field set. “Any XML or JSON feed” overstates arbitrary schema compatibility. No arbitrary custom-attribute preservation exists in the feed parser.
10. **The readiness audit is a sample/source audit.** It checks robots rules, fetched HTML for Product JSON-LD, GTIN/SKU coverage, content depth, and generated-feed eligibility. It does not run a browser or a dedicated bot-wall diagnostic; inaccessible sampled pages become a warning. Brand checks are in the separate 34-rule listing audit.

- Research totals and ratios, DUA visit result/permission, anonymized spirits findings, programme participation, and Google access approval rely on supplied evidence. Code cannot independently validate those commercial/history facts.
- ChatGPT app directory publication, current third-party channel programs/eligibility and logo permissions need primary-source/owner verification, not inference from ecentic code.
- Plugin publication, plugin-level `created_via` behavior and currently deployed gateway support need plugin/deployment evidence for stronger claims.
- Precise hosting regions, encryption at rest, TLS minimums, data retention operational guarantees, DPA availability, security pack, support SLA, roadmap commitments and agency commercial terms need owner evidence.
- Enterprise audit/pilot staffing, durations, question counts, deliverables and method are service commitments, not code features. Do not assert unconfirmed bracketed values.
